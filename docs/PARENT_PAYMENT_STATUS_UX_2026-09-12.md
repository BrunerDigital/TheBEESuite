## Implementation and recovery contract

- Complete already-authorized Stripe/Terminal DRAFT scope feeds a sanitized phase/method DTO. Off-page attempts remain visible; family-wide blockers explain both balance and invoice holds. Home retains the actual remaining amount/credit/review state; its attention link and recent-payment rows use accurate status labels.
- Active provider records missing usable family/invoice attribution fail closed as account-wide blockers. They never label an arbitrary invoice paid. Shared claims and UI use the same predicate; inactive/manual/failed/void records remain nonblocking.
- Both parent Checkout handlers synchronously reserve a local attempt. Conflicts, server/network failures and malformed success receipts latch confirmation pending. Only a same-origin server receipt with explicit `ok: true`, valid local payment ID, `cs_` Session ID and an absolute HTTPS destination without credentials or nonstandard port permits navigation; late responses cannot redirect a different family or unmounted workspace. This validates the server response contract, not an arbitrary URL's ownership. Both server paths source the destination and Session ID from Stripe. Stripe-supported custom Checkout domains remain compatible; no provider hostname is inferred from portal branding. [Stripe Session URL contract](https://docs.stripe.com/api/checkout/sessions/object), [custom domains](https://docs.stripe.com/payments/checkout/custom-domains).
- New `GET /api/parent/payment-status` requires the exact parent role, an explicit currently linked/eligible family and account-scoped invoice/payment targets. It returns complete scoped sanitized observations with a correlation nonce and private/no-store headers. Invoice IDs from metadata are checked against account ownership. Request and response bodies are omitted from operational logs. No Stripe calls, expiry, reconciliation, ledger changes or writes occur.
- Empty observations do **not** prove that a lost POST failed. A missing receipt, failed/void/returned/disputed/contradictory receipt stays unresolved. An exact unambiguous PAID receipt permits only a deliberate fresh-page balance review, never automatic reuse of the old amount. Unknown attempts without a receipt need school review if they never resolve; durable client-attempt correlation across entirely lost responses is separate server hardening.
- Status requests are canceled/superseded across family changes, new submissions and unmount. Wrong nonce/scope, malformed responses and errors retain the hold. Concurrent full-account observations merge scope flags, counts and exact-invoice maps conservatively; new invoice B can be held without disabling unrelated C. No-charge method setup remains separate.
- Browser tests use real components/CSS and fake-only intercepted requests, including initial-clear to 503/409, contradictory success, double taps, empty/error/mismatched refreshes, exact-invoice versus family scope, stale family observations and late Checkout navigation. No actual payment or production fixture mutation is used.
